# MSME Assistant — Architecture

> Per project spec (Mistake #7): keep this doc split clearly into
> "Implemented" vs "Vision / Roadmap". Never claim a roadmap-only item
> (GST automation, live WhatsApp/banking integration) is built.

## Business Model

MSME Assistant models a small **trading/reselling MSME** — e.g. a hardware
or building-materials distributor. The business buys stock from
suppliers, holds inventory, and resells it to business customers on
30-day credit terms (not cash-on-sale retail). That credit relationship
is exactly why payment-delay risk exists as a problem worth solving —
if every sale were paid instantly, there would be no invoices to chase.
This is a deliberate scope choice, not a limitation: MSME Assistant does not
attempt to model manufacturers, service businesses, or pure cash-retail
shops as-is.

## Core Loop

Model predicts → Twin simulates outcome → Rule engine validates →
Approval queue (if needed) → Execute (or draft for human review)

## Implemented

- [x] Data schema — 7 tables: products, sales_history, customers,
      invoices, suppliers, cash_ledger, decisions
- [x] Synthetic data generation — 20 products, 8 suppliers, 50
      customers, ~13.5k sales rows (2 years, with seasonality), 400
      invoices (noisy/overlapping payment-behavior distributions with
      amount and seasonal-cash-crunch interaction effects), ~14k cash
      ledger entries
- [x] Demand forecasting model — statsmodels Holt-Winters
      (Exponential Smoothing), chosen over Prophet after Prophet's
      C++/Stan build toolchain failed to install on Windows. Beats a
      7-day static-threshold baseline by 5.6% MAE / 7.0% RMSE,
      averaged across all 20 products.
- [x] Payment-delay prediction model — XGBoost classifier with
      leakage-safe expanding-window customer features (avg past
      delay, invoice count) and a time-based train/test split.
      Compared against a static-rule baseline ("flag late if
      customer's past avg delay > 3 days"). Result on an 80-invoice
      time-based test split: essentially a statistical tie (XGBoost
      F1 0.813 vs baseline F1 0.818) — reported honestly rather than
      re-tuned to force a win. See Evaluation Metrics for detail and
      why this is still a legitimate result.
- [x] Simulation layer (the "digital twin") — simulate_reorder()
      computes projected cash and stock impact of a proposed reorder,
      using a recent (30-day) demand rate and a stockout-risk label
      (high/medium/low by days-of-stock-remaining). This is a real
      computation from proposed action to projected state, not a
      lookup.
- [x] Rule / safety engine — check_reorder() validates a simulated
      outcome against a minimum cash floor, a maximum single-purchase
      fraction of current cash, and whether stockout risk actually
      improves. Returns auto_approved / flagged / rejected. Verified
      against 3 hand-picked cases (safe reorder, cash-floor-violating
      oversized reorder, undersized reorder that doesn't fix the
      risk) plus live use through the API.
- [x] Approval queue UI — propose a reorder, see it auto-execute or
      appear in a pending queue, approve/reject flagged items.
- [x] Decision log / replay view (Decision History page) — every
      reorder, sale, and stock adjustment ever made, filterable by
      status and action type, each traceable back to its simulated
      outcome.
- [x] Per-product history — click any product to see its own
      filtered timeline of everything that's touched its stock.
- [x] Dashboard — single-glance business health: cash balance,
      products below threshold / at high risk, pending approvals,
      unpaid/overdue invoice counts and total.
- [x] Invoices / Collections page — unpaid invoices ranked by risk
      using each customer's historical average payment delay.
- [x] Record Sale — decrements stock, appends to sales_history (so
      future forecasts see it), logs revenue to the cash ledger.
      Rejects overselling.
- [x] Manual Stock Adjustment — corrects stock for stocktaking or
      damaged-goods discrepancies without touching cash.
- [x] LLM-assisted drafting (draft-only, clearly labeled) — uses the
      real Anthropic API (Claude Sonnet 4.5):
    - Collections reminder drafting, with a button per invoice
    - Vendor email drafting, on the Suppliers page
    - WhatsApp-style order message parsing (product name + quantity
      extraction) — parsing aid only, does not write to the database
  All three return draft text only. Nothing is ever sent
  automatically; every response includes an explicit
  "nothing has been sent" note.

## Known Limitations (honest, not hidden)

- All results are validated on **synthetic data only**, generated by
  this project's own data generator. Metrics like "beats baseline by
  X%" are true for this synthetic world; they are not yet validated
  against a real business's actual data.
- Reorder purchase price uses each product's fixed, static
  `unit_cost` — it does not yet vary per purchase (negotiated price,
  bulk discount, supplier chosen). Record Sale does support an
  optional per-sale price override; reorders do not have the
  equivalent yet.
- Suppliers exist as a table and are shown in the Suppliers page, but
  reorder logic does not yet let the owner pick which supplier to buy
  from — it's product-based only.
- Rule engine safety thresholds (minimum cash floor, max purchase
  fraction) are hardcoded constants in `rule_engine.py`, not yet
  owner-configurable via the UI.
- Single-user, local-only (SQLite on one machine). No authentication,
  no multi-business data isolation, no deployment. This is a
  deliberate, separate future phase — see Vision / Roadmap.

## Vision / Roadmap (documented only, not built)

- GST automation
- Autonomous month-end closing
- Live WhatsApp Business API integration
- Live banking / GSP integrations
- Authentication + multi-user data isolation (likely via Supabase —
  hosted Postgres with built-in auth)
- Real deployment (backend on Railway/Render, frontend on
  Vercel/Netlify)
- Full CRUD on products (add new product, edit name/price, delete)
- Owner-configurable safety rule thresholds
- Supplier-aware reordering (pick which supplier to buy from)
- Supplier risk scoring model (optional stretch, per original spec)
- Transaction anomaly detection (optional stretch, per original spec)

## Data Disclosure

All data used in this project is synthetically generated. No real
business, customer, or transaction data was used.
